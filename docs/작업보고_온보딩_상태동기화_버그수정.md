## 1. 실제 확인된 버그 목록

### 1) 체크리스트 상태 모델 오류 (FE에 SKIPPED가 섞여 있음)
- **원인**: FE `checklist/page.tsx`가 `PENDING → DONE → SKIPPED → PENDING` 3단계 순환 UI("건너뜀" 탭 포함)를 구현하고 있었고, `lib/api.ts`의 `ItemStatus`가 `PENDING|DONE|SKIPPED|DISMISSED` 하나로 세 도메인(계획/체크리스트/추천)에 공유되어 잘못된 값을 컴파일 단계에서 막지 못함. BE `ChecklistService`도 `DONE`이 아니면 무조건 `markPending()`으로 처리해, `SKIPPED`를 보내면 조용히 `PENDING`이 되어 사용자에게 "건너뜀으로 변경했다"는 토스트만 보이고 실제로는 대기 상태가 됨.
- **재현**: 체크리스트에서 "상태 변경" → "다음 상태로 변경(건너뜀)" 클릭 → 토스트는 "건너뜀"이라 뜨지만 목록 재조회 후 상태는 `PENDING`.
- **수정**: FE 체크리스트 화면에서 "건너뜀" 탭·필터·액션 전부 제거(체크박스 완료/완료취소는 유지). `lib/api.ts`의 `ItemStatus`를 `PlanItemStatus`(`PENDING|DONE|SKIPPED`) / `ChecklistStatus`(`PENDING|DONE`) / `RecommendationStatus`(`PENDING|DONE|DISMISSED`)로 분리해 각 API 함수·DTO에 맞는 타입만 쓰도록 함. BE `ChecklistService.updateChecklist`와 `OnboardingPlanService.updateItemStatus`에 상태 화이트리스트 검증을 추가해, 허용되지 않는 상태를 보내면 조용히 변환하지 않고 `400 VALIDATION_ERROR`로 명확히 거부.

### 2) 상태 동기화가 단방향으로만 동작
- **원인**: 체크리스트 → 계획 항목 동기화는 있었지만(`ChecklistService`), 계획 항목 → 체크리스트(`OnboardingPlanService.updateItemStatus`)와 추천 → 계획/체크리스트, 계획 → 추천 동기화가 없거나 일부만 존재. 세 서비스가 각자 `recalculateProgress`를 중복 구현하고 있어 로직도 어긋나기 쉬운 구조였음.
- **재현**: 체크리스트 DONE → 30일 계획에서도 DONE 확인 → 30일 계획에서 "완료 취소" → 체크리스트는 여전히 DONE (화면 이동 시 불일치).
- **수정**: `OnboardingSyncService`(신규)를 만들어 "PlanItem·ChecklistItem·(dismiss되지 않은) DailyRecommendation을 같은 done/pending 상태로 맞추고 계획 진행률을 재계산"하는 로직을 한 곳에 모음. `ChecklistService`, `OnboardingPlanService`, `RecommendationService`가 각자의 진입점(체크리스트 갱신 / 계획 항목 갱신 / 추천 완료)에서 이 서비스 하나만 호출하도록 정리하고, 3곳에 중복돼 있던 `recalculateProgress`를 제거.

### 3) 대시보드 첫 진입에서 오늘 할 일이 0개로 보일 수 있음
- **원인**: `DashboardService.me()`가 `@Transactional(readOnly = true)`였고, 추천이 아직 없을 때도 `RecommendationService.todayReadOnly()`(생성 없이 조회만)를 호출해 계획 생성 직후 대시보드에 들어가면 오늘 할 일이 비어 보였음.
- **재현**: 계획 생성 → 바로 `GET /dashboard/me` 호출 → `today.total = 0`.
- **수정**: `DashboardService.me()`에서 `@Transactional(readOnly = true)`를 제거하고, 오늘 추천이 없으면 생성까지 책임지는 `RecommendationService.today()`(쓰기 가능한 자신의 트랜잭션에서 동작)를 직접 호출하도록 변경. 읽기 전용 트랜잭션 안에서 쓰기를 강제로 밀어넣지 않고, "오늘 추천이 반드시 존재하게 만드는" 책임을 `RecommendationService`로 명확히 옮김. 더 이상 쓰이지 않는 `todayReadOnly()`는 삭제.

### 4) 오늘 할 일 fallback 추천의 FK 위반 위험
- **원인**: 오늘 배정된 계획 항목이 없을 때, `RecommendationService`가 저장하지 않는 임시 `OnboardingPlanItem`(`UUID.randomUUID()`로 생성, DB에 INSERT 안 함)을 만들고 `DailyRecommendation.fromPlanItem()`으로 그 임시 id를 `plan_item_id` FK에 그대로 복사해 저장을 시도. `daily_recommendations.plan_item_id`는 `onboarding_plan_items(id)` FK라 존재하지 않는 UUID로 INSERT하면 위반.
- **재현**: 템플릿 항목이 없는 날짜(day)에 `GET /recommendations/today?date=...` 호출.
- **수정**: `DailyRecommendation`에 `planItemId = null`을 명시적으로 쓰는 `fallback(...)` 팩터리를 추가하고, 저장하지 않는 임시 `OnboardingPlanItem` 생성 코드를 완전히 제거. fallback 추천은 `source = "SYSTEM"`, `planItemId = null`로 안전하게 생성·완료된다.

### 5) 추천 건너뛰기(DISMISSED) 후에도 화면에 계속 남음
- **원인**: `GET /recommendations/today`는 DISMISSED를 포함한 전체 목록을 그대로 반환하고, FE `daily-tasks` 화면이 `items`를 그대로 섹션에 렌더링해 "건너뛰기"를 눌러도 카드가 사라지지 않음. (화면 안내 문구는 이미 "건너뛴 항목은 오늘 추천에서 빠집니다"라고 되어 있어, 제품 의도는 A(숨김)로 이미 정해져 있었음)
- **수정(FE 쪽, B안 선택)**: API 계약(응답에 DISMISSED 포함)은 유지하고, FE에서 문서/체크리스트/실습 섹션과 "추천 순서" 목록을 만들 때 `status !== 'DISMISSED'`인 항목만 사용하도록 필터링. 진행률(`완료/전체`)도 이 필터된 목록 기준으로 계산해, 사용자가 건너뛴 항목 때문에 분모가 부풀어 진행률이 낮아 보이는 문제도 함께 없앰. "제외 N" 배지는 전체 목록 기준으로 별도 유지. dismiss된 추천은 기존 로직(`existing.isEmpty()`일 때만 재생성) 덕분에 다시 생성되지 않음(변경 없음, 기존 동작 확인).

### 6) "+ 추천 다시 받기" 버튼이 실제로는 단순 새로고침
- **원인**: 버튼이 `load()`(기존 `GET /recommendations/today` 재호출)만 수행하는데 문구는 "새로 받기"처럼 보임. 서버에 추천 재생성 API가 없음.
- **수정**: 문구를 "추천 새로고침"으로 변경하고, 실제 동작(재조회)이라는 주석을 남김. 새 재생성 API는 만들지 않음(요청사항대로).

### 7) DOCUMENT 템플릿 UX와 BE validation 불일치
- **원인**: FE `TemplateItemsEditor`가 DOCUMENT 타입에 "연결 안 함" 옵션을 허용했고, 저장 시 `documentId`가 없으면 payload에서 필드 자체를 생략해 BE가 `400 "DOCUMENT 항목에는 documentId가 필요합니다."`로 거부. 사용자는 저장 버튼을 누르기 전까지 문제를 알 수 없었음.
- **수정**: "연결 안 함" 옵션 제거. READY 문서가 0개면 항목 유형 셀렉트에서 `DOCUMENT` 옵션을 비활성화하고, 항목별로 "먼저 처리 완료된 문서를 업로드해야 저장할 수 있습니다" 안내를 표시. 문서를 아직 못 고른 DOCUMENT 항목은 셀렉트 테두리를 빨간색으로 표시하고 "문서를 선택해야 저장할 수 있습니다" 안내를 노출. 템플릿 생성/편집/AI초안 저장(`handleCreate`/`handleUpdate`/`handleSaveDraft`) 3곳 모두에서 저장 직전 `findUnlinkedDocumentItem()`으로 막아 400을 아예 받지 않게 함. BE validation(`TemplateService.saveItems`)은 변경하지 않음.

### 8) 템플릿 Editor `key={index}` 문제
- **원인**: 항목 추가/삭제/이동 시 React가 index 기반 key로 DOM을 재사용해 입력 포커스가 다른 행으로 튀는 것처럼 보임.
- **수정**: 편집기 전용 안정 key(`_key`)를 가진 `EditableTemplateItem` 타입을 도입. 서버에서 불러온 기존 항목은 서버 item id를, 새로 추가한 항목은 `crypto.randomUUID()`를 `_key`로 사용. 렌더링 `key`를 `item._key`로 교체. 저장 시(`toSavePayload`)는 항상 새 객체를 조립해 보내므로 `_key`는 API payload에 포함되지 않음(계약 불변).

### 9) 30일 계획의 완료/완료취소 버튼 검증
- 체크리스트에서 먼저 DONE으로 만든 뒤 30일 계획으로 이동하면, 이제 `OnboardingSyncService`가 즉시 계획 항목도 DONE으로 맞추므로 "완료 취소" 버튼이 정상적으로 보이고 클릭도 가능함 (버그 2)의 수정으로 자동 해결).
- "완료 취소" 시 체크리스트도 PENDING으로 돌아가는지, 하루 전체 완료/취소 시 연결 체크리스트가 함께 바뀌는지 통합 테스트(Scenario A/B)로 확인.
- `updatingItemId`는 컴포넌트 로컬 `useState`라 페이지 이동(리마운트) 시 자동 초기화됨을 코드로 확인 — 별도 수정 불필요.
- `handleToggleDay`는 이미 부분 실패 시 `catch` 블록에서 `await load()`로 서버 상태를 다시 읽어오고 있어(기존 코드), 최소 요구사항 충족을 확인만 하고 변경하지 않음.

### 10) 진행률 정의 혼동
- **원인**: 대시보드와 체크리스트 화면이 서로 다른 지표(전체 온보딩 진행률 vs 체크리스트 완료율)를 똑같이 "진행률/완료율"이라는 애매한 이름으로 노출.
- **수정**: BE 계산 로직은 이미 일관됨(둘 다 `plan.progressPercent`를 SSOT로 사용하는 `/progress`, `/admin/progress`와, `checklist_items` 기준으로 별도 계산하는 체크리스트 완료율 — 애초에 다른 지표를 다른 이름으로 보여줘야 하는 게 맞음). FE 표기만 명확히 분리: 대시보드 카드 제목을 "전체 온보딩 진행률"로, 체크리스트 화면의 라벨을 "완료율" → "체크리스트 완료율"로 변경(카드 헤더·모달 타이틀 포함).

### 11) `ItemStatus` 공통 타입 과도한 공유
- 위 1)에서 함께 처리: `PlanItemStatus` / `ChecklistStatus` / `RecommendationStatus`로 분리하고 관련 DTO·함수 시그니처를 모두 갱신.

### 12) 오래된 DOCUMENT 템플릿 데이터 호환성
- 확인 결과 FE `selectableTemplates()`(30day-plan 화면에서 계획 생성용 템플릿 후보를 거를 때 씀)와 BE `OnboardingPlanService`의 `explicitTemplate`/`legacyTestMode` 분기 호환 로직은 이번 작업에서 **손대지 않음**. 템플릿 편집 화면에서는 7)의 수정 덕분에 `documentId=null`인 DOCUMENT 항목이 있는 레거시 템플릿을 열어도 깨지지 않고, "문서를 선택해야 저장할 수 있습니다"로 명확히 안내되며 문서를 연결해야만 저장할 수 있음.

### 14) 추가 코드 리뷰에서 발견/정리한 것
- `ChecklistService`, `OnboardingPlanService`, `RecommendationService`에 중복돼 있던 `recalculateProgress` 3벌을 `OnboardingSyncService` 하나로 통합(중복 로직 제거).
- `RecommendationService.today()`/구 `todayReadOnly()`가 워크스페이스/유저 스코프 쿼리를 쓰고 있는 것은 이미 올바름 — 격리 누락 없음을 확인.

## 3. 상태 동기화 최종 규칙

세 엔티티(`OnboardingPlanItem` / `ChecklistItem` / `DailyRecommendation`)는 모두 `OnboardingSyncService.syncCluster(workspaceId, userId, planItemId, done)` 한 곳을 거쳐 동기화됩니다. 진입점은 세 군데뿐입니다.

```
체크리스트 PATCH (PENDING/DONE)
  → 이 체크리스트 항목 자신을 먼저 바꾼다
  → syncCluster(planItemId, done)
      → 연결된 PlanItem 을 같은 상태로
      → 그 PlanItem 에 연결된, dismiss 되지 않은 오늘의 Recommendation 을 같은 상태로
      → Plan.progressPercent 재계산

계획 항목(PlanItem) PATCH (PENDING/DONE)
  → syncCluster(planItemId, done)
      → 이 PlanItem 자신을 바꾼다
      → 연결된 ChecklistItem 을 같은 상태로
      → 연결된, dismiss 되지 않은 Recommendation 을 같은 상태로
      → Plan.progressPercent 재계산

추천(Recommendation) 완료 (POST /complete)
  → 이 Recommendation 자신을 DONE 으로
  → syncCluster(planItemId, done=true)
      → 연결된 PlanItem 을 DONE 으로
      → 연결된 ChecklistItem 을 DONE 으로
      → Plan.progressPercent 재계산

추천 dismiss (건너뛰기)
  → 이 Recommendation 만 DISMISSED 로. PlanItem/ChecklistItem 은 건드리지 않는다
    (사용자가 "이 항목은 안 하겠다"는 의사표시일 뿐, 실제 완료 여부와는 무관하기 때문)
```

규칙:
- **이미 목표 상태인 항목은 다시 쓰지 않는다.** (`completedAt`이 호출마다 갱신되는 걸 막기 위함 — 여러 경로에서 반복 호출돼도 타임스탬프가 흔들리지 않음)
- **DISMISSED 인 추천은 절대 건드리지 않는다.** 다른 경로(체크리스트/계획 항목)에서 상태가 바뀌어도 사용자가 명시적으로 건너뛴 추천을 다시 살리지 않는다.
- **`planItemId`가 없으면 아무 것도 하지 않는다.** (fallback 추천처럼 계획 항목과 연결되지 않은 독립 항목)
- 체크리스트는 여전히 `PENDING|DONE`만, 계획 항목은 `PENDING|DONE|SKIPPED`(이번 작업에서 API 단은 `PENDING|DONE`만 허용 — 아래 "6. 수정하지 않은 항목" 참고)만, 추천은 `PENDING|DONE|DISMISSED`만 허용한다는 DB CHECK 제약은 그대로 유지된다.

## 4. Template DOCUMENT validation 최종 UX

1. 항목 유형을 `DOCUMENT`로 선택하려는데 READY 문서가 하나도 없으면, 유형 드롭다운에서 `DOCUMENT` 옵션 자체가 비활성화된다.
2. `DOCUMENT` 유형을 고르면 "연결 문서" 셀렉트가 항상 나타나고, 첫 옵션은 선택 불가능한 placeholder(`문서를 선택하세요` / `연결 가능한 문서 없음`)다 — "연결 안 함"은 없다.
3. 문서를 아직 못 고른 상태면 셀렉트 테두리가 빨간색이 되고, 그 아래 안내 문구("문서를 선택해야 저장할 수 있습니다" 또는 "먼저 처리 완료(READY)된 문서를 업로드해야 이 항목을 저장할 수 있습니다")가 보인다.
4. 생성/편집/AI초안 저장 버튼을 눌러도, 연결되지 않은 `DOCUMENT` 항목이 하나라도 있으면 저장 요청 자체를 보내지 않고 토스트로 어느 항목인지 알려준다.
5. BE는 그대로 `documentId` 없는 `DOCUMENT` 항목을 `400 VALIDATION_ERROR`로 거부한다(직접 API를 호출하는 경우를 위한 최종 방어선, 변경 없음).
6. 비-DOCUMENT 유형으로 바꾸면 `documentId`는 즉시 제거된다(기존 동작 유지).

## 6. 수정하지 않은 항목

| 항목 | 이유 | 향후 위험 |
|---|---|---|
| 계획 항목 상태 API에서 `SKIPPED` 값 지원 | DB/도메인은 `SKIPPED`를 지원하지만, 실제로 이 값을 세팅하는 서비스 로직·FE 화면이 어디에도 없었음(코드 전수조사 결과 `ItemStatus.SKIPPED`를 세팅하는 코드는 진행률 계산의 분모 제외용으로만 쓰임). 없는 기능을 새로 만들지 않기 위해, `PATCH /onboarding-plans/items/{id}`는 `PENDING`/`DONE`만 허용하도록 방어적으로 좁혔습니다. | 나중에 "계획 항목 건너뛰기" 기능이 요구되면, `OnboardingPlanItem.markSkipped()`와 이 엔드포인트의 화이트리스트를 함께 넓혀야 합니다. |
| FE 테스트 프레임워크(Jest/Vitest) 신규 도입 | 기존에 전혀 없던 인프라를 이번 버그 수정 범위에서 새로 들이는 것은 과도한 확장이라고 판단 | 템플릿 에디터(Scenario H) 같은 DOM 상호작용 회귀는 자동 테스트로 못 잡고, `tsc`/`build`/수동 확인에 의존합니다. |

| Admin/Progress 화면들의 "진행률" 문구 전수 정리 | `/dashboard/progress`(진행 현황)와 `/admin/progress`는 원래도 `plan.progressPercent` 하나만 쓰고 있어 혼동 사례가 아니었음. 요청 범위(대시보드·체크리스트)만 정리했습니다 | 없음(애초에 문제였던 두 화면만 수정) |
