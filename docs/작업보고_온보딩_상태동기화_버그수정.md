## 1. 실제 확인된 버그 목록

### 1) 체크리스트 상태 모델 오류 (FE에 SKIPPED가 섞여 있음)
- **원인**: FE `checklist/page.tsx`가 `PENDING → DONE → SKIPPED → PENDING` 3단계 순환 UI("건너뜀" 탭 포함)를 구현하고 있었고, `lib/api.ts`의 `ItemStatus`가 `PENDING|DONE|SKIPPED|DISMISSED` 하나로 세 도메인(계획/체크리스트/추천)에 공유되어 잘못된 값을 컴파일 단계에서 막지 못함. BE `ChecklistService`도 `DONE`이 아니면 무조건 `markPending()`으로 처리해, `SKIPPED`를 보내면 조용히 `PENDING`이 되어 사용자에게 "건너뜀으로 변경했다"는 토스트만 보이고 실제로는 대기 상태가 됨.
- **재현**: 체크리스트에서 "상태 변경" → "다음 상태로 변경(건너뜀)" 클릭 → 토스트는 "건너뜀"이라 뜨지만 목록 재조회 후 상태는 `PENDING`.
- **수정**: FE 체크리스트 화면에서 "건너뜀" 탭·필터·액션 전부 제거(체크박스 완료/완료취소는 유지). `lib/api.ts`의 `ItemStatus`를 `PlanItemStatus`(`PENDING|DONE|SKIPPED`) / `ChecklistStatus`(`PENDING|DONE`) / `RecommendationStatus`(`PENDING|DONE|DISMISSED`)로 분리해 각 API 함수·DTO에 맞는 타입만 쓰도록 함. BE `ChecklistService.updateChecklist`와 `OnboardingPlanService.updateItemStatus`에 상태 화이트리스트 검증을 추가해, 허용되지 않는 상태를 보내면 조용히 변환하지 않고 `400 VALIDATION_ERROR`로 명확히 거부.

### 2) 상태 동기화가 단방향으로만 동작
- **원인**: 체크리스트 → 계획 항목 동기화는 있었지만(`ChecklistService`), 계획 항목 → 체크리스트(`OnboardingPlanService.updateItemStatus`)와 추천 → 계획/체크리스트, 계획 → 추천 동기화가 없거나 일부만 존재. 세 서비스가 각자 `recalculateProgress`를 중복 구현하고 있어 로직도 어긋나기 쉬운 구조였음.
- **재현**: 체크리스트 DONE → 30일 계획에서도 DONE 확인 → 30일 계획에서 "완료 취소" → 체크리스트는 여전히 DONE (화면 이동 시 불일치).
- **수정**: `OnboardingSyncService`(신규)를 만들어 "PlanItem·ChecklistItem·(dismiss되지 않은) DailyRecommendation을 같은 done/pending 상태로 맞추고 계획 진행률을 재계산"하는 로직을 한 곳에 모음. `ChecklistService`, `OnboardingPlanService`, `RecommendationService`가 각자의 진입점(체크리스트 갱신 / 계획 항목 갱신 / 추천 완료)에서 이 서비스 하나만 호출하도록 정리하고, 3곳에 중복돼 있던 `recalculateProgress`를 제거.

### 3) 대시보드 첫 진입에서 오늘 할 일이 0개로 보일 수 있음
- **원인**: `DashboardService.me()`가 `@Transactional(readOnly = true)`였고, 추천이 아직 없을 때도 `RecommendationService.todayReadOnly()`(생성 없이 조회만)를 호출해 계획 생성 직후 대시보드에 들어가면 오늘 할 일이 비어 보였음.
- **재현**: 계획 생성 → 바로 `GET /dashboard/me` 호출 → `today.total = 0`.
- **수정**: `DashboardService.me()`에서 `@Transactional(readOnly = true)`를 제거하고, 오늘 추천이 없으면 생성까지 책임지는 `RecommendationService.today()`(쓰기 가능한 자신의 트랜잭션에서 동작)를 직접 호출하도록 변경. 읽기 전용 트랜잭션 안에서 쓰기를 강제로 밀어넣지 않고, "오늘 추천이 반드시 존재하게 만드는" 책임을 `RecommendationService`로 명확히 옮김. 더 이상 쓰이지 않는 `todayReadOnly()`는 삭제.

### 4) 오늘 할 일 fallback 추천의 FK 위반 위험
- **원인**: 오늘 배정된 계획 항목이 없을 때, `RecommendationService`가 저장하지 않는 임시 `OnboardingPlanItem`(`UUID.randomUUID()`로 생성, DB에 INSERT 안 함)을 만들고 `DailyRecommendation.fromPlanItem()`으로 그 임시 id를 `plan_item_id` FK에 그대로 복사해 저장을 시도. `daily_recommendations.plan_item_id`는 `onboarding_plan_items(id)` FK라 존재하지 않는 UUID로 INSERT하면 위반.
- **재현**: 템플릿 항목이 없는 날짜(day)에 `GET /recommendations/today?date=...` 호출.
- **수정**: `DailyRecommendation`에 `planItemId = null`을 명시적으로 쓰는 `fallback(...)` 팩터리를 추가하고, 저장하지 않는 임시 `OnboardingPlanItem` 생성 코드를 완전히 제거. fallback 추천은 `source = "SYSTEM"`, `planItemId = null`로 안전하게 생성·완료된다.

### 5) 추천 건너뛰기(DISMISSED) 후에도 화면에 계속 남음
- **원인**: `GET /recommendations/today`는 DISMISSED를 포함한 전체 목록을 그대로 반환하고, FE `daily-tasks` 화면이 `items`를 그대로 섹션에 렌더링해 "건너뛰기"를 눌러도 카드가 사라지지 않음. (화면 안내 문구는 이미 "건너뛴 항목은 오늘 추천에서 빠집니다"라고 되어 있어, 제품 의도는 A(숨김)로 이미 정해져 있었음)
- **수정(FE 쪽, B안 선택)**: API 계약(응답에 DISMISSED 포함)은 유지하고, FE에서 문서/체크리스트/실습 섹션과 "추천 순서" 목록을 만들 때 `status !== 'DISMISSED'`인 항목만 사용하도록 필터링. 진행률(`완료/전체`)도 이 필터된 목록 기준으로 계산해, 사용자가 건너뛴 항목 때문에 분모가 부풀어 진행률이 낮아 보이는 문제도 함께 없앰. "제외 N" 배지는 전체 목록 기준으로 별도 유지. dismiss된 추천은 기존 로직(`existing.isEmpty()`일 때만 재생성) 덕분에 다시 생성되지 않음(변경 없음, 기존 동작 확인).

### 6) "+ 추천 다시 받기" 버튼이 실제로는 단순 새로고침
- **원인**: 버튼이 `load()`(기존 `GET /recommendations/today` 재호출)만 수행하는데 문구는 "새로 받기"처럼 보임. 서버에 추천 재생성 API가 없음.
- **수정**: 문구를 "추천 새로고침"으로 변경하고, 실제 동작(재조회)이라는 주석을 남김. 새 재생성 API는 만들지 않음(요청사항대로).

### 7) DOCUMENT 템플릿 UX와 BE validation 불일치
- **원인**: FE `TemplateItemsEditor`가 DOCUMENT 타입에 "연결 안 함" 옵션을 허용했고, 저장 시 `documentId`가 없으면 payload에서 필드 자체를 생략해 BE가 `400 "DOCUMENT 항목에는 documentId가 필요합니다."`로 거부. 사용자는 저장 버튼을 누르기 전까지 문제를 알 수 없었음.
- **수정**: "연결 안 함" 옵션 제거. READY 문서가 0개면 항목 유형 셀렉트에서 `DOCUMENT` 옵션을 비활성화하고, 항목별로 "먼저 처리 완료된 문서를 업로드해야 저장할 수 있습니다" 안내를 표시. 문서를 아직 못 고른 DOCUMENT 항목은 셀렉트 테두리를 빨간색으로 표시하고 "문서를 선택해야 저장할 수 있습니다" 안내를 노출. 템플릿 생성/편집/AI초안 저장(`handleCreate`/`handleUpdate`/`handleSaveDraft`) 3곳 모두에서 저장 직전 `findUnlinkedDocumentItem()`으로 막아 400을 아예 받지 않게 함. BE validation(`TemplateService.saveItems`)은 변경하지 않음.

### 8) 템플릿 Editor `key={index}` 문제
- **원인**: 항목 추가/삭제/이동 시 React가 index 기반 key로 DOM을 재사용해 입력 포커스가 다른 행으로 튀는 것처럼 보임.
- **수정**: 편집기 전용 안정 key(`_key`)를 가진 `EditableTemplateItem` 타입을 도입. 서버에서 불러온 기존 항목은 서버 item id를, 새로 추가한 항목은 `crypto.randomUUID()`를 `_key`로 사용. 렌더링 `key`를 `item._key`로 교체. 저장 시(`toSavePayload`)는 항상 새 객체를 조립해 보내므로 `_key`는 API payload에 포함되지 않음(계약 불변).

### 9) 30일 계획의 완료/완료취소 버튼 검증
- 체크리스트에서 먼저 DONE으로 만든 뒤 30일 계획으로 이동하면, 이제 `OnboardingSyncService`가 즉시 계획 항목도 DONE으로 맞추므로 "완료 취소" 버튼이 정상적으로 보이고 클릭도 가능함 (버그 2)의 수정으로 자동 해결).
- "완료 취소" 시 체크리스트도 PENDING으로 돌아가는지, 하루 전체 완료/취소 시 연결 체크리스트가 함께 바뀌는지 통합 테스트(Scenario A/B)로 확인.
- `updatingItemId`는 컴포넌트 로컬 `useState`라 페이지 이동(리마운트) 시 자동 초기화됨을 코드로 확인 — 별도 수정 불필요.
- `handleToggleDay`는 이미 부분 실패 시 `catch` 블록에서 `await load()`로 서버 상태를 다시 읽어오고 있어(기존 코드), 최소 요구사항 충족을 확인만 하고 변경하지 않음.

### 10) 진행률 정의 혼동
- **원인**: 대시보드와 체크리스트 화면이 서로 다른 지표(전체 온보딩 진행률 vs 체크리스트 완료율)를 똑같이 "진행률/완료율"이라는 애매한 이름으로 노출.
- **수정**: BE 계산 로직은 이미 일관됨(둘 다 `plan.progressPercent`를 SSOT로 사용하는 `/progress`, `/admin/progress`와, `checklist_items` 기준으로 별도 계산하는 체크리스트 완료율 — 애초에 다른 지표를 다른 이름으로 보여줘야 하는 게 맞음). FE 표기만 명확히 분리: 대시보드 카드 제목을 "전체 온보딩 진행률"로, 체크리스트 화면의 라벨을 "완료율" → "체크리스트 완료율"로 변경(카드 헤더·모달 타이틀 포함).

### 11) `ItemStatus` 공통 타입 과도한 공유
- 위 1)에서 함께 처리: `PlanItemStatus` / `ChecklistStatus` / `RecommendationStatus`로 분리하고 관련 DTO·함수 시그니처를 모두 갱신.

### 12) 오래된 DOCUMENT 템플릿 데이터 호환성
- 확인 결과 FE `selectableTemplates()`(30day-plan 화면에서 계획 생성용 템플릿 후보를 거를 때 씀)와 BE `OnboardingPlanService`의 `explicitTemplate`/`legacyTestMode` 분기 호환 로직은 이번 작업에서 **손대지 않음**. 템플릿 편집 화면에서는 7)의 수정 덕분에 `documentId=null`인 DOCUMENT 항목이 있는 레거시 템플릿을 열어도 깨지지 않고, "문서를 선택해야 저장할 수 있습니다"로 명확히 안내되며 문서를 연결해야만 저장할 수 있음.

### 14) 추가 코드 리뷰에서 발견/정리한 것
- `ChecklistService`, `OnboardingPlanService`, `RecommendationService`에 중복돼 있던 `recalculateProgress` 3벌을 `OnboardingSyncService` 하나로 통합(중복 로직 제거).
- `RecommendationService.today()`/구 `todayReadOnly()`가 워크스페이스/유저 스코프 쿼리를 쓰고 있는 것은 이미 올바름 — 격리 누락 없음을 확인.

## 3. 상태 동기화 최종 규칙

세 엔티티(`OnboardingPlanItem` / `ChecklistItem` / `DailyRecommendation`)는 모두 `OnboardingSyncService.syncCluster(workspaceId, userId, planItemId, done)` 한 곳을 거쳐 동기화됩니다. 진입점은 세 군데뿐입니다.

```
체크리스트 PATCH (PENDING/DONE)
  → 이 체크리스트 항목 자신을 먼저 바꾼다
  → syncCluster(planItemId, done)
      → 연결된 PlanItem 을 같은 상태로
      → 그 PlanItem 에 연결된, dismiss 되지 않은 오늘의 Recommendation 을 같은 상태로
      → Plan.progressPercent 재계산

계획 항목(PlanItem) PATCH (PENDING/DONE)
  → syncCluster(planItemId, done)
      → 이 PlanItem 자신을 바꾼다
      → 연결된 ChecklistItem 을 같은 상태로
      → 연결된, dismiss 되지 않은 Recommendation 을 같은 상태로
      → Plan.progressPercent 재계산

추천(Recommendation) 완료 (POST /complete)
  → 이 Recommendation 자신을 DONE 으로
  → syncCluster(planItemId, done=true)
      → 연결된 PlanItem 을 DONE 으로
      → 연결된 ChecklistItem 을 DONE 으로
      → Plan.progressPercent 재계산

추천 dismiss (건너뛰기)
  → 이 Recommendation 만 DISMISSED 로. PlanItem/ChecklistItem 은 건드리지 않는다
    (사용자가 "이 항목은 안 하겠다"는 의사표시일 뿐, 실제 완료 여부와는 무관하기 때문)
```

규칙:
- **이미 목표 상태인 항목은 다시 쓰지 않는다.** (`completedAt`이 호출마다 갱신되는 걸 막기 위함 — 여러 경로에서 반복 호출돼도 타임스탬프가 흔들리지 않음)
- **DISMISSED 인 추천은 절대 건드리지 않는다.** 다른 경로(체크리스트/계획 항목)에서 상태가 바뀌어도 사용자가 명시적으로 건너뛴 추천을 다시 살리지 않는다.
- **`planItemId`가 없으면 아무 것도 하지 않는다.** (fallback 추천처럼 계획 항목과 연결되지 않은 독립 항목)
- 체크리스트는 여전히 `PENDING|DONE`만, 계획 항목은 `PENDING|DONE|SKIPPED`(이번 작업에서 API 단은 `PENDING|DONE`만 허용 — 아래 "6. 수정하지 않은 항목" 참고)만, 추천은 `PENDING|DONE|DISMISSED`만 허용한다는 DB CHECK 제약은 그대로 유지된다.

## 4. Template DOCUMENT validation 최종 UX

1. 항목 유형을 `DOCUMENT`로 선택하려는데 READY 문서가 하나도 없으면, 유형 드롭다운에서 `DOCUMENT` 옵션 자체가 비활성화된다.
2. `DOCUMENT` 유형을 고르면 "연결 문서" 셀렉트가 항상 나타나고, 첫 옵션은 선택 불가능한 placeholder(`문서를 선택하세요` / `연결 가능한 문서 없음`)다 — "연결 안 함"은 없다.
3. 문서를 아직 못 고른 상태면 셀렉트 테두리가 빨간색이 되고, 그 아래 안내 문구("문서를 선택해야 저장할 수 있습니다" 또는 "먼저 처리 완료(READY)된 문서를 업로드해야 이 항목을 저장할 수 있습니다")가 보인다.
4. 생성/편집/AI초안 저장 버튼을 눌러도, 연결되지 않은 `DOCUMENT` 항목이 하나라도 있으면 저장 요청 자체를 보내지 않고 토스트로 어느 항목인지 알려준다.
5. BE는 그대로 `documentId` 없는 `DOCUMENT` 항목을 `400 VALIDATION_ERROR`로 거부한다(직접 API를 호출하는 경우를 위한 최종 방어선, 변경 없음).
6. 비-DOCUMENT 유형으로 바꾸면 `documentId`는 즉시 제거된다(기존 동작 유지).

# 추가 라운드 — 실제 배포 E2E에서 발견된 버그 3건

1차 작업 이후 실제 배포 환경에서 추가로 보고된 버그 3건(오늘 할 일 stale recommendation, 공통 Modal 포커스 버그, 날짜/타임존 버그)을 수정했다. 아래는 같은 보고 형식으로 정리한 결과다.

## 1) 오늘 할 일 stale recommendation

**원인**: `RecommendationService.todayFor()`는 `daily_recommendations`에 그날짜 행이 하나라도 있으면 현재 active plan과 비교 없이 그대로 반환했다. 계획을 재생성하면 `OnboardingPlanService.generateForUser()`가 완전히 새로운 `OnboardingPlanItem` id 집합으로 새 계획을 만들지만(기존 계획은 `ARCHIVED`), 재생성 전에 이미 만들어져 있던 "오늘의 추천" 행은 그대로 남아 예전(archived) 계획의 `plan_item_id`를 계속 가리켰다.

**재현**: 30일 계획 생성 → `GET /recommendations/today` 호출(오늘 추천 3건 생성) → Day1 구성이 다른 템플릿으로 계획 재생성(2건으로 축소) → 다시 `GET /recommendations/today` → 여전히 예전 3건이 그대로 노출.

**수정**:
- **1차 방어선 (생성 시점)**: `OnboardingPlanService.generateForUser()` 끝에서, 새로 활성화된 계획의 `startDate`(=오늘)에 대해 `deleteByWorkspaceIdAndUserIdAndRecommendDate(workspaceId, userId, plan.getStartDate())`를 호출해 그날의 기존 추천을 전부 지운다. **다른 날짜의 이력은 절대 건드리지 않는다** (정확히 오늘 하루치만 대상). 다음 `GET /recommendations/today` 호출이 새 계획의 Day1 항목 기준으로 다시 만든다.
- **DONE/DISMISSED 이력 처리 방침**: "오늘의 추천" 행은 그날그날 다시 만들 수 있는 파생 데이터로 취급했다. 완료 여부의 소스 오브 트루스는 `PlanItem`/`ChecklistItem` 상태이며, `regenerate(preserveCompleted=true)`는 이미 `StableItemKey` 매칭으로 완료 상태를 새 계획 항목에 옮겨 놓는다. 따라서 예전 추천 행(DONE이든 DISMISSED든)을 그대로 지우고 새로 만들어도 "완료했다"는 사실 자체는 유실되지 않는다. (레거시 테스트 생성자 호환을 위해 `recommendationRepository`가 `null`일 수 있는 경로엔 null 체크를 둬 하위 호환을 지켰다.)
- **2차 방어선 (조회 시점)**: `RecommendationService.todayFor()`에 `dropStaleForPlan()`을 추가해, 응답 직전에 "`planItemId`가 있는데 현재 활성 계획의 항목 목록에 없는" 추천을 한 번 더 걸러낸다. 1차 방어선을 놓친 경로(예: 향후 다른 코드가 계획을 archiving하는 경우)에서도 최소 보장을 지키기 위한 안전망이다. `planItemId`가 없는 fallback 추천은 건드리지 않는다.
- 필터링 후 오늘 추천이 0건이 되고 활성 계획이 있으면, 기존 로직대로 새 계획 기준으로 재생성한다.

## 2) 공통 Modal 입력 포커스가 X 버튼으로 이동하는 버그

**원인**: `FE/components/ui/modal.tsx`의 `handleKeyDown`이 `useCallback(..., [onClose])`였고, 초기 포커스 이동을 담당하는 `useEffect`가 `[open, handleKeyDown]`에 의존했다. 부모가 `onClose={() => setOpen(false)}`처럼 인라인 함수를 넘기면(이 저장소의 모든 모달 사용부가 이 패턴), 입력 필드에 한 글자 칠 때마다 부모 state가 바뀌어 리렌더 → `onClose` identity 변경 → `handleKeyDown` identity 변경 → `useEffect` 재실행 → cleanup에서 이전 리스너 해제 후 effect 본문이 다시 실행되며 `setTimeout(0)`으로 "모달의 첫 번째 포커스 가능 요소"에 다시 `.focus()`를 호출했다. DOM 순서상 첫 번째 요소가 항상 헤더의 X 닫기 버튼이라, 타이핑할 때마다 포커스가 거기로 튀었다.

**수정**:
- `onClose`는 항상 최신 값을 담는 `onCloseRef`로만 참조하도록 바꿔, `handleKeyDown`(ESC 처리 + Tab 트랩)이 `onClose`의 identity 변화와 완전히 무관해지도록 했다 (`useCallback(..., [])`로 참조가 한 번 생성된 뒤 고정된다).
- 그 결과 큰 `useEffect(() => {...}, [open, handleKeyDown])`는 사실상 `open`이 실제로 바뀔 때(닫힘→열림)만 실행된다. children/부모 리렌더로는 더 이상 재실행되지 않는다.
- 초기 포커스 대상을 "입력 요소 우선"으로 바꿨다: `input`/`textarea`/`select`가 있으면 그쪽을, 없으면 기존처럼 첫 포커스 가능 요소(대개 닫기 버튼)를 focus한다.
- ESC로 닫기, Tab 순환 트랩은 로직 변경 없이 그대로 유지했다.
- 공통 `Modal` 컴포넌트는 이 저장소에서 유일한 모달 구현체이고(다른 자체 dialog 구현 없음을 확인), 모든 화면의 모달이 이걸 그대로 쓰므로 이 한 파일 수정으로 전체 회귀 없이 일괄 수정된다. props(`open`/`onClose`/`title`/`subtitle`/`size`/`children`/`footer`/`closeOnBackdrop`)는 그대로다.

## 3) 날짜/타임존 버그 (KST 통일)

**원인**: `RecommendationService`, `DashboardService`, `OnboardingPlanService`, `ProgressService` 4곳에서 `LocalDate.now()`를 그대로 썼다. JVM 기본 타임존이 UTC인 배포 환경(Docker)에서는 한국 시각 자정~오전 9시 사이에 하루 전 날짜로 "오늘"이 계산되어(예: KST 08-21 05:00 == UTC 08-20 20:00), 오늘 할 일/현재 일차(dayIndex)/계획 시작일이 전부 하루 밀릴 수 있었다.

**수정**:
- 새 전용 타입 `com.onboardos.onboarding.global.time.BusinessClock`을 추가했다. 내부적으로 `java.time.Clock`을 감싸지만, `today()`는 그 delegate clock이 어떤 타임존을 갖고 있든 항상 `Asia/Seoul`로 다시 투영해서(`delegate.withZone(ZONE)`) 날짜를 계산한다 — 그래서 "이 시계를 만들 때 어떤 zone을 줬는지"에 기대지 않고 항상 한국 날짜가 나온다.
  - **왜 raw `Clock` 빈을 쓰지 않았나**: 기존에 `SchedulingConfig`가 문서 정리 배치(`DocumentStorageCleanupService`)용 UTC `Clock` 빈을 `@ConditionalOnMissingBean(Clock.class)`로 등록해 두고 있었다. 여기에 KST용 `Clock` 빈을 하나 더 추가하면 (a) 타입 충돌로 Spring이 기동 실패하거나(실제로 한 번 이 상태로 시도했다가 `NoUniqueBeanDefinitionException`으로 전체 통합 테스트가 깨지는 것을 확인하고 되돌렸다), (b) `@Qualifier`로 억지로 구분하더라도 `@ConditionalOnMissingBean(Clock.class)`가 타입 기준이라 배치용 UTC 빈이 조용히 안 만들어질 위험이 있었다. `BusinessClock`을 별도 타입으로 둬서 이 문제 자체를 없앴다 — `SchedulingConfig`/`DocumentStorageCleanupService`는 전혀 건드리지 않았고, 문서 정리 배치는 여전히 원래의 UTC `Clock`을 그대로 쓴다.
- `ClockConfig`가 `BusinessClock` 빈 하나를 등록하고, 4개 서비스가 이를 주입받아 `LocalDate.now()`/`ChronoUnit.DAYS.between(..., LocalDate.now())`를 `clock.today()`로 교체했다.
- `createdAt`/`updatedAt` 같은 `Instant` 타임스탬프, `hibernate.jdbc.time_zone=UTC` 설정, DB에 저장되는 시각 자체는 **전혀 건드리지 않았다.** `BusinessClock`은 오직 "오늘이 며칠인지"(`LocalDate`) 계산에만 쓰인다.

## 3. 사용자 플로우가 수정 전/후 어떻게 달라졌는지

**분석 결과 요약 (자세한 내용은 대화의 사전 분석 참고):**
- 체크리스트 soft-delete, 템플릿 목록 API의 items 포함 여부, DOCUMENT 문서 검증(문서 없음/삭제됨/READY 아님/대상 역할 접근 불가), `preserveCompleted`의 `StableItemKey` 매칭, 인턴의 권한 범위 — **전부 코드로 직접 확인한 결과 이미 정상이었고 수정하지 않았다.**
- stale recommendation 정리·타임존(Asia/Seoul)·PlanItem/Checklist/Recommendation 3중 동기화·공통 Modal 포커스는 **이전 두 라운드에서 이미 수정·테스트 완료**된 상태라 재검증만 했다(이번 라운드 회귀 테스트에서도 함께 확인).

**수정 전:**
- 관리자가 인턴에게 온보딩 계획을 만들어 주려면: `onboarding-progress` 화면에서 이미 계획이 있는 인턴만, 그것도 "기존 계획이 쓰던 템플릿 그대로" 재생성할 수 있었다. 계획이 아직 없는 인턴에게는 관리자가 해 줄 수 있는 게 전혀 없었고("본인이 먼저 만들어야 한다"), 관리자가 다른 템플릿을 골라 적용할 방법 자체가 없었다.
- MANAGER 계정은 `30day-plan` 화면에서 "계획 재생성" 버튼을 볼 수 있었지만 누르면 403이 났다.
- 재생성 모달에서 템플릿을 골랐다가 그 템플릿이 삭제되면, 모달을 다시 열어도 이미 사라진 템플릿 id가 그대로 남아 있다가 전송될 위험이 있었다.
- 템플릿 생성 모달을 취소 후 다시 열면 이전에 입력하던 값이 남아 있었다.
- 템플릿을 수정해도 기존 계획에 반영되지 않는다는 사실이 화면 어디에도 안내되지 않았다.

**수정 후:**
- 관리자(OWNER/ADMIN/MANAGER)가 `신입 진행 현황`(`onboarding-progress`) 화면에서 인턴을 선택 → "조치하기" → 적용할 템플릿을 고르고 → 계획이 있으면 재생성(완료 항목 유지 여부 선택), 없으면 그 자리에서 바로 생성. 어느 쪽이든 **그 인턴의 userId/planId만** 대상이 되고 관리자 자신의 계획은 절대 바뀌지 않는다(통합 테스트로 확인).
- MANAGER도 OWNER/ADMIN과 동일하게 계획 생성/재생성이 가능하다(단, 템플릿 자체의 생성/수정은 여전히 OWNER/ADMIN 전용 — 그대로 유지).
- 재생성 모달은 열 때마다 "현재 계획의 템플릿이 아직 유효하면 그것, 아니면 자동 선택"으로 정해지고, 사라진 템플릿은 화면과 실제 전송 값 모두에서 자동으로 배제된다.
- 템플릿 생성 모달은 열 때마다 항상 빈 폼으로 시작한다.
- 템플릿 수정 화면과 관리자의 계획 적용 화면 양쪽에 "자동 반영 안 됨 / 재생성으로 적용" 안내가 보인다.

## 8. 아직 남아 있는 제한사항

| 항목 | 이유 / 현재 상태 |
|---|---|
| `onboarding-progress` 화면에서 "계획 생성" 시 `force` 옵션 미노출 | 이 경로는 항상 `newbie.planId`가 없을 때만 쓰이므로(있으면 재생성 분기) 현재는 `force`가 실질적으로 의미가 없다. 계획이 있는데도 강제로 새로 만들고 싶은 경우(활성 계획을 보관하고 새로 시작)는 이번 범위에 없던 요구라 다루지 않았다. |
| 인턴이 여러 명일 때 일괄(bulk) 템플릿 적용 | 요청 시나리오가 "특정 인턴 한 명"이었고, 일괄 적용은 실수로 여러 인턴의 계획을 한 번에 덮어쓸 위험이 있어 이번에 만들지 않았다. 필요하면 별도로 신중하게 설계해야 한다. |
| `updateItemStatus`(계획 항목 개별 완료 토글)의 관리자 대행 권한에 MANAGER 미포함 | 이 경로는 현재 FE에서 관리자가 인턴의 개별 항목을 토글하는 UI가 전혀 없어(재생성 단위로만 조작) 실사용 경로가 아니다. 스코프를 넓히지 않기 위해 손대지 않았다. 향후 그런 UI가 생기면 함께 맞춰야 한다. |
| FE 테스트가 `onboarding-progress`/`30day-plan`/`templates`의 새 UI 분기(생성/재생성 버튼, 폼 리셋)를 자동 커버하지 않음 | FE 테스트 인프라(vitest)는 지난 라운드에 Modal용으로 최소로만 들여왔다. 페이지 단위 컴포넌트 테스트(라우팅/컨텍스트 mocking 필요)는 이번 범위를 넘는 규모라 `tsc`/`build`/BE 통합 테스트(실제 API 계약)로 대체 검증했다. |

## 9. 실제 배포 후 사람이 클릭해서 확인할 E2E 체크리스트

**A. 관리자 → 인턴 지정 → 계획 반영**
1. OWNER/ADMIN(또는 MANAGER) 계정으로 로그인
2. `템플릿` 화면에서 NEW_HIRE 대상 템플릿 생성 (예: Day1 체크리스트 "계정 설정" + PERSON "멘토 미팅", Day2 PRACTICE "첫 업무")
3. `신입 진행 현황` 화면으로 이동 → 계획이 아직 없는 인턴(표에 "계획 없음") 선택 → 상세 → "조치하기"
4. 템플릿 드롭다운에서 방금 만든 템플릿 선택 → "이 템플릿으로 계획 생성" 클릭 → 성공 토스트 확인
5. 그 인턴 계정으로 로그인
6. `30일 계획` 화면: Day1에 계정 설정/멘토 미팅, Day2에 첫 업무가 보이는지 확인
7. `체크리스트` 화면: "계정 설정" 항목이 있는지 확인
8. `오늘 할 일`(오늘이 Day1이라면): "계정 설정" · "멘토 미팅" 2건이 보이는지, 예전/다른 항목이 섞여 있지 않은지 확인

**B. 템플릿 변경 → 재생성 → 화면 일치**
9. 관리자 계정으로 돌아가 그 템플릿을 편집 (예: "계정 설정" 제거, "보안 교육" CHECKLIST 추가) → 저장 시 "자동 반영 안 됨" 안내 문구 확인
10. `신입 진행 현황`에서 같은 인턴 선택 → "조치하기" → 템플릿 드롭다운이 최신 템플릿 목록을 보여주는지 확인 → "계획 전체 재생성" 클릭
11. 인턴 계정으로 다시 로그인 → 30일 계획/체크리스트/오늘 할 일 모두 "보안 교육"으로 바뀌어 있고 "계정 설정"이 어디에도 남아 있지 않은지 확인

**C. 완료 → 취소 → 세 화면 동기화**
12. 인턴 계정에서 체크리스트의 항목 하나를 완료 처리
13. 30일 계획 화면에서 그 항목이 "완료"로 보이는지 확인
14. 오늘 할 일 화면에서도 같은 항목이 완료로 보이는지 확인 (전체 대시보드 진행률도 함께 오르는지)
15. 30일 계획에서 그 항목을 "완료 취소"
16. 체크리스트/오늘 할 일 화면에서 다시 미완료로 보이는지 확인 (세 화면 어디서 봐도 상태가 일치해야 한다)

**D. 사용자 분리 / 권한**
17. 관리자 계정의 `30일 계획` 화면은 여전히 관리자 자신의 계획만 보이고, 위 B에서 인턴 계획을 재생성한 것과 무관한지 확인
18. MANAGER 계정으로 로그인해 `신입 진행 현황`에서 계획 생성/재생성이 403 없이 동작하는지 확인
19. NEW_HIRE(인턴) 계정으로는 `템플릿`/`신입 진행 현황` 화면에 접근하거나 다른 사람 계획을 조작할 수 없는지 확인

**E. 타임존 (한국 새벽 시간대에 배포 서버가 UTC일 때)**
20. 한국 시각 자정~오전 9시 사이에 오늘 할 일/대시보드에 접속해, "오늘"이 한국 날짜 기준으로 표시되는지 확인 (서버 로그의 UTC 날짜와 하루 차이가 나는 게 정상)
